# 01. 요구사항

## 핵심 키워드

| 키워드 | 한 줄 설명 |
|---|---|
| 멀티 회원 | 회원마다 자기 증권 계좌·전략·주문·예수금을 따로 가진다 |
| BrokerClient | 증권사 연동을 인터페이스로 감춰서 Fake(장애 주입) ↔ KIS(실제)를 갈아끼운다 |
| 주문 정합성 | 타임아웃·재시도·동시 요청 속에서도 중복 주문, 잔고 초과가 생기지 않는다 |
| UNKNOWN 상태 | "들어갔는지 모르는" 주문을 따로 두고, 대조(reconciliation)로 확정한다 |
| 예수금 hold | 주문 전에 금액을 묶어서 동시 매수로 잔고를 넘지 않게 한다 |

## 1. 목표

- 여러 회원이 각자 한국투자증권 모의투자 계좌를 연결하고 전략을 등록하면, 서버가 장 시간에 자동으로 매매한다.
- 외부 API 장애(지연, 거절, 응답 유실, 호출 제한, 연결 끊김)를 **일부러 재현**하고 해결 과정을 기록한다.

## 2. 기능 요구사항 (MVP)

### 회원·인증
- 회원가입 (이메일, 비밀번호, 닉네임). 비밀번호는 BCrypt.
- 로그인 → JWT 발급. 이후 요청은 `Authorization: Bearer` 헤더.
- 내 정보 조회.

### 증권 계좌 연결
- 회원은 증권 계좌 1개를 연결한다: 증권사 종류(`FAKE` / `KIS`), 앱키, 앱시크릿, 계좌번호.
- 앱키·앱시크릿은 **암호화해서 저장**, 응답에는 절대 노출하지 않는다.
- 연결 테스트 API (토큰 발급 + 잔고 조회가 되는지).
- KIS 접근 토큰은 계좌별로 저장·재사용하고, 만료 전에 갱신한다.

### 계좌
- 예수금(전체 / 묶인 금액 / 주문 가능 금액) 조회.
- 보유 종목(수량, 평균단가) 조회.

### 주문
- 수동 주문: 종목, 매수/매도, 수량, 가격(지정가).
- 주문 전 리스크 체크: 종목당 최대 투자금, 하루 최대 주문 수 (회원별).
- 주문 목록(페이징) / 상세 조회. 상세에는 상태 변경 이력 포함.
- 응답을 못 받은 주문은 `UNKNOWN` → 대조 스케줄러가 증권사 주문 목록으로 확정.

### 전략·자동매매
- 전략 등록: 종류(MVP는 이동평균 교차 1개), 종목, 단기/장기 기간, 1회 주문 금액.
- 전략 활성화 / 비활성화, 내 전략 목록.
- 장 시간(평일 09:00~15:30)에만 활성 전략 실행: 시세 → 전략 신호 → 리스크 → 주문.

## 3. 비기능 요구사항

| 항목 | 기준 |
|---|---|
| 중복 주문 | 응답 유실 30% 상황에서 주문 100건 → 중복 0건 |
| 잔고 초과 | 동시 매수 요청 다수 → 주문 가능 금액 초과 0건 |
| 호출 제한 | 증권사 초당 호출 제한을 넘지 않음 |
| 보안 | 앱키·시크릿·JWT 비밀키는 코드/저장소에 없음, DB에는 암호화 |
| 테스트 | 도메인 로직(상태 머신, hold, 전략)은 단위 테스트, 주요 API는 통합 테스트. PR마다 CI 통과 |

## 4. MVP에서 제외 (나중에)

- 실전투자 계좌, 시장가 주문, 정정·취소 주문
- 전략 여러 종류, 백테스트
- 알림(이메일/슬랙), 프론트엔드
- 서버 2대 이상, Redis (→ M6)

## 5. 결정 사항

| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 회원별로 자기 KIS 앱키를 등록 | 실제 서비스에 가깝고, 회원별 토큰 관리·암호화 저장이라는 고민거리가 생김 | 서버 계좌 하나로 모든 회원 주문 → 회원 간 체결 구분이 불가능 |
| 기본 증권사는 FAKE | 앱키 없이도 개발·테스트 가능, 장애를 마음대로 주입 | 처음부터 KIS만 → 장 시간에만 테스트 가능, 장애 재현 불가 |
| 탈퇴는 논리 삭제(deletedAt) | 주문 기록은 지우면 안 됨 | 물리 삭제 |
